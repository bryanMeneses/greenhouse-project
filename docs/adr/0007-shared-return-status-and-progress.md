# Shared return status: one canonical progress model, audience-adapted presentation

Challenge 06 wants a status that "means the same thing to everyone" — clients and firm staff reading one return the same way. The trap is building two status concepts that drift. We reject that: there is **one canonical progress model, presented per audience**. Preparer and Client read the same Stage, the same open items, the same blockers; 06 changes only the wording and the level of detail, never the truth underneath. This is already the shape the code leans toward — `Stage` is shared, and the thin client `ReturnStatus` translates it — so 06 formalizes that arrangement rather than inventing a parallel one.

**The model borrows 07's, read-only — no schema change.** `Stage` (`intake → in-review → ready-to-file`) stays the coarse source of truth that `rankDashboard` (challenge 07) sorts on; expanding the enum would ripple into ranking and its tests for no gain. Richness is _derived_, not stored: a pure `deriveReturnStatus(taxReturn, now)` produces audience-agnostic facts — the current step, who a return is blocked on, the open items grouped by owner, and the deadline state (overdue / near / clear). Wording and the single-action-vs-list choice live in the components; the logic is unit-tested like `ranking.ts`. 06 consumes the existing `Return` / `OpenItem` model without adding fields.

**The tracker is a stepper over the three Stages, plus a finish line.** A horizontal stepper mirrors the three `Stage` values 1:1 — inventing intermediate steps the model can't back is how a tracker starts lying — with a dimmed, always-upcoming "Filed" marker as the visible destination (every seed Return is pre-filing). Same three positions for both audiences; labels adapt (client "Getting started" / preparer "Intake") — _same step, different word_ is the whole demonstration that status means the same thing to everyone. The completed steps _are_ "what's already happened"; a full event log is deliberately out of scope.

**Blocking, next action, and deadline are derived and audience-relative.** "Blocked" is not a stored flag — a return is blocked, for a given viewer, when an open item is owned by someone _other_ than them (client sees "we need X from you," preparer sees "waiting on client: X"). Blocking is orthogonal to lifecycle position, so it renders as a separate amber callout beside the stepper, never as a step; amber reads as a _wait_, leaving red for an overdue deadline. The Client sees a single primary "what's next for you," with reassurance when nothing is on them; the Preparer, who juggles many items, sees the grouped list with blockers emphasized. The `deadline` is framed for the Client ("On track to file before Sep 15" / "we need X to stay on track") and shown raw with overdue/near flags for the Preparer.

**Two surfaces, one module.** The Preparer gets a status band at the top of the return-view — standing context while they work the return. The Client's existing `return-status-page` is formalized: the stepper sits above the current "Waiting on you / With your preparer" groups, with the primary next-action call-out under it. Both consume the one `deriveReturnStatus` module. The stepper is hand-built from design-system tokens (shadcn has no stepper primitive, so this doesn't violate the shadcn-first rule of ADR-0002); the stage pill can migrate to the shadcn `Badge`.

**Scope guard.** 06 is the _per-return_ status experience for two Roles — **Preparer** and **Client** — only. Reviewer and Firm Admin read status at the _portfolio_ level, which is challenge 07's dashboard, not this. The existing seed is reused unchanged: the roster already carries blocked-on-client, preparer-only, and a clean `ready-to-file` Return (Underwood), covering every state including the celebratory terminal one. The "no return yet" client empty state stays.

**Consequence.** Status becomes a derived read over the existing model, so any later challenge that changes a Return's Stage, open items, or deadline updates both audiences' status for free — there is no second place to keep in sync. Because blocking and the next action are computed from open-item ownership, challenge 02 (collaboration) can make a return blocked simply by adding a client-owned open item, and the status experience reflects it without new plumbing.
