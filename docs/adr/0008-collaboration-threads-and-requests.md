# Collaboration: contextual Threads, and Requests as client-owned Open Items

Challenge 02 wants a collaboration layer that ties conversation to specific documents and issues, separates internal firm notes from client-visible messages, tracks outstanding requests, and shows who owns the next action — without becoming "just another generic inbox." The trap is a global message stream and a parallel task concept that drifts from the work. We reject both: collaboration is **contextual by construction**, and an outstanding request is **not a new object** but an Open Item read through its audience.

**A Thread anchors to exactly one Subject; there is no free-floating conversation.** A Subject is one of a Return, a Source Document, or an Open Item — the "documents or tax issues" the brief names. Not a Field: a question about a single extracted value rolls up to its Source Document or becomes an Open Item, because field-level threads would shatter one conversation into hundreds of fragments (that is 09's scale problem, not collaboration's). This anchoring is what keeps the layer from degrading into a generic inbox — every message has a place it belongs.

**A Request is an Open Item whose owner is a Client Role — the same object, named for its audience.** The glossary already defines Open Item as "an outstanding action on a Return, with a clear owner and urgency," which is verbatim what "track outstanding requests" and "who owns the next action" ask for. Adding a `Request` object would split "outstanding action" into two overlapping concepts that drift. Instead: the firm asking a client for a document, an answer, or a signature _is_ an Open Item owned by that client. "Who owns the next action" on any Thread is simply that Open Item's owner. This is the model ADR-0004 promised 03 would consume — 03's first-run next-action list is these Requests, not a throwaway task list.

**A Request's lifecycle keeps a human in the loop; ownership is always the next action.** Open (owner: Client) → the client acts (upload / answer / e-sign) → ownership flips to the Preparer → the Preparer verifies and closes → Closed. Fulfillment is the _action_, not an in-thread reply (a reply is optional context). There is no auto-close on client action — the firm always verifies, so "who owns next" is answerable at every moment. This reuses Open Item's existing `owner` and `urgency`; the only addition is a `Closed` resolution. Because status blocking (ADR-0007) is already derived from open-item ownership, adding a client-owned Open Item makes the return blocked-on-client for free, and the ownership flip surfaces it to the Preparer with no new plumbing.

**Visibility is per-Message, and the boundary is rendered through the 05 role switch, not a second build.** Each Message carries one Message audience — Internal (firm-only) or Client-visible — so one Thread can hold both, and an internal note can live inside a client-visible conversation. The Preparer sees everything and composes with an **audience-aware control** (Internal / Client-visible, defaulting to the safer choice for the context — the anti-leak affordance is itself part of what 02 grades). The Client, via the existing role switch on the _same_ Return, sees only Client-visible Messages and only their own Requests, and composes with no audience toggle (client messages are always Client-visible). The demonstration is a live toggle on one thread holding an Internal note — it vanishes for the Client — reusing 05 rather than building a parallel client surface.

**Contextual-first, per-Return, no global message inbox.** Threads render in place on their Subject (a discussion on a Source Document, on an Open Item, and a Return-level one). Each Return workspace gets one aggregation surface — a **"Requests & Activity"** panel that leads with that return's open Requests (client-owned Open Items, by urgency) and then recent messages: organized around outstanding actions, never a chronological dump. There is deliberately no cross-client inbox. Cross-return surfacing is 07's job: a client action flips an Open Item back to the Preparer, and _that_ Open Item is what the dashboard ranks. That single decision is the whole answer to "don't build a generic inbox" — no undifferentiated message list exists anywhere.

**Scope and seed.** The existing seeded Return (the one behind `returns/review` and `client-view`) is reused. Seed three Threads — one on a Source Document (a W-2 question), one on an Open Item/Request ("upload your 1098"), one Return-level — with Messages mixing Client-visible and at least one Internal note _inside_ a client-visible thread (the boundary test). Three Open Items span the lifecycle — one Open (owner: Client), one flipped to Preparer, one Closed — so "who owns next" varies. Two screens: the Preparer Return workspace (Requests & Activity panel + an open thread across both audiences + audience-aware compose), and the Client view of the same Return via role switch. New code lands as a collaboration slice under `features/returns` per the feature-first structure (ADR-0006), with the Thread component shared across the review and client-view surfaces. No messaging backend — hardcoded messages, optimistic send.

**Consequence.** Collaboration adds one genuinely new object — the Thread with its audience-tagged Messages — and otherwise leans entirely on the existing Return / Open Item model. Because a Request is just a client-owned Open Item, challenges 03 (first-run next actions), 06 (blocking/status), and 07 (dashboard ranking) all read collaboration state through machinery they already have; there is no second source of truth to keep in sync. The cost of this unification is that "Request" has no independent identity in the data — it is a view over Open Item — which every consumer must understand; the glossary carries that definition so the naming does not mislead.
