# Routing with react-router; routes compose split features

> **Superseded in part by [ADR-0006](0006-feature-first-file-structure.md).** The three-layer `routes/` / `features/` / `components/` split described below was later reorganized: the `routes/` layer was dissolved into per-feature pages (`*-page.tsx`), `features/return-review` folded into `features/returns/review`, and the shell moved under `components/layout`. The routing choices here — react-router, the `/returns` → `/` redirect, the single Dashboard nav item, and the shared `features/returns` domain kernel — all still hold; only the folder layout changed.

We added client-side routing with **react-router** (`/` → dashboard, `/returns/:returnId` → that Return's review) and reorganized `src/` around three layers: `routes/` holds route-level composition and route-only UI; `features/<domain>/` holds domain logic and reusable UI; `components/` holds the shared shell and ui primitives. A layout-free `main.tsx` mounts `RouterProvider` from a `router.tsx` route tree. This replaces the old `useState` toggle in `App.tsx`, which had no URLs and no deep-linking.

We chose react-router because it's the de-facto standard for React SPAs, its data-router API (`createBrowserRouter` / `RouterProvider`) is a small, well-understood surface, and `Link` / `useParams` / `useLocation` give us deep-linkable routes and active-route nav (`aria-current="page"`) for free — the whole point of the change. A bare `/returns` (no id) has no page of its own — the dashboard is the list — so it redirects to `/` rather than 404-ing.

The sidebar carries a single **Dashboard** nav item pointing at `/`; it stays current across `/returns/:id` too, because a Return's review is a drill-in from the dashboard rather than a separate destination. We dropped the earlier separate "Returns" item as redundant (it only ever led back to the same ranked list). **Review Queue** is shown as a disabled "Soon" hint, not a link: today the Review Queue is a section _inside_ a single Return's review, so a top-level entry would overpromise a cross-Return surface that doesn't exist yet.

**Implementer's call — shared `features/returns` core.** We extracted the Returns domain model (returns, field-state, confidence, provenance, review-queue, source-documents) into `features/returns/`, which both `features/dashboard` and `features/return-review` depend on. The dashboard only needs the Return/Field types and `reviewQueue` — the domain, not the review UI — so the alternative (dashboard importing from its sibling `features/return-review`) would have coupled two peer features through their UI folder. A shared domain kernel keeps the dependency direction clean: features depend on the domain, never on each other.
